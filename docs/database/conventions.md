# Database conventions

Applies to every table. Source rules: `CLAUDE.md` §6.

## Keys and tenancy
- Primary key `id UUID` (`UUIDPrimaryKeyMixin`). No sequential IDs in URLs or public links.
- Every organisation-owned table has `organisation_id UUID NOT NULL` with a foreign key and an index. Branch-owned tables also have `branch_id`.
- Human-facing document numbers (job cards, quotations, invoices) are separate columns, unique per organisation: `UNIQUE (organisation_id, number)`. They are allocated from a per-organisation sequence table inside the creating transaction.

## Types
| Data | Type |
|---|---|
| Money | `NUMERIC(14,2)` (`Money` annotation). Never float. |
| Currency | `CHAR(3)` ISO code on every financial document, default `NAD` |
| Quantities (stock) | `NUMERIC(12,3)` (litres of oil, metres of hose) |
| Timestamps | `TIMESTAMPTZ`, stored UTC, displayed in the organisation time zone (default `Africa/Windhoek`) |
| Emails | `CITEXT` |
| Statuses | `TEXT` + `CHECK` constraint listing allowed values; transitions enforced in services |

## Constraints and naming
Constraint names come from `NAMING_CONVENTION` in `app/db/base.py`, so autogenerated migrations are deterministic:

- `pk_<table>`, `fk_<table>_<column>_<referred_table>`, `uq_<table>_<columns>`, `ck_<table>_<name>`, `ix_<table>_<column>`

## Deletion
- Business and financial records are never hard-deleted. Use `archived_at TIMESTAMPTZ NULL` (or `is_active`) instead.
- Foreign keys to financial, stock or audit records use `ON DELETE RESTRICT`.

## Migrations
- Every schema change is an Alembic revision in `backend/migrations/versions/`.
- Review autogenerated migrations by hand before committing.
- `uv run alembic check` must report no pending changes in CI.
- Migrations must be reversible where practical, and must test `upgrade → downgrade → upgrade`.
